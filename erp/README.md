# پورتال ERP چندشرکتی (فارسی / راست‌به‌چپ)

یک ERP سبک و قابل‌استقرار برای چند شرکت مستقل (Multi-tenant) روی یک سرور.
**پیش‌فرض بدون وابستگی خارجی** — فقط Node.js ≥ 22.13 (SQLite داخلی Node)؛ برای مقیاس بزرگ‌تر **PostgreSQL** (بسته‌ی اختیاری `pg`). تاریخ‌ها شمسی نمایش داده و ورودی گرفته می‌شوند.

## اجرا

```bash
cd erp
npm run seed:demo      # (اختیاری) شرکت نمونه با داده‌ی آزمایشی؛ کاربران demo_admin … demo_viewer، گذرواژه demo1234
npm start              # http://localhost:3000
npm test               # ۶۱ تست عملکردی + ۲۱ امنیتی + ۹ پشتیبان‌گیری + XSS در مرورگر (در صورت وجود playwright) یکپارچگی (ایزولاسیون شرکت‌ها، RBAC، گردش کار، حسابداری، تولید)
```

در اولین اجرا حساب `superadmin` ساخته می‌شود و گذرواژه‌ی تصادفی آن در کنسول چاپ می‌شود
(یا با متغیر `ERP_SUPERADMIN_PASSWORD` تعیین کنید). سپس: **شرکت‌ها ← شرکت جدید** (انتخاب ماژول‌های فعال + ساخت مدیر شرکت).

| متغیر محیطی | کاربرد | پیش‌فرض |
|---|---|---|
| `PORT` / `HOST` | آدرس سرویس | `3000` / `0.0.0.0` |
| `ERP_DATA_DIR` | مسیر دیتابیس (`erp.db`) و کلید نشست | `erp/data` |
| `DATABASE_URL` | آدرس PostgreSQL (`postgres://user:pass@host/db`)؛ خالی = SQLite | — |
| `PGPOOL` | حداکثر اتصال همزمان PostgreSQL | `10` |
| `ERP_FILES_DIR` | مسیر فایل‌های پیوست | `<data>/files` |
| `ERP_MAX_UPLOAD_MB` | حداکثر حجم هر پیوست | `10` |
| `ERP_TRUST_PROXY` | تعداد پراکسی‌های مورد اعتماد جلوی برنامه (مثلاً `1`)؛ فقط پشت پراکسی تنظیم شود | `0` |
| `ERP_COOKIE_SECURE` | `1` = کوکی همیشه Secure | — |
| `ERP_RATE_PER_MIN` | سقف درخواست API به‌ازای IP در دقیقه | `600` |
| `ERP_BACKUP_DIR` / `ERP_BACKUP_KEEP` / `ERP_BACKUP_KEY` / `ERP_BACKUP_HOOK` | پشتیبان‌گیری (رجوع به DEPLOY.md) | `<data>/backups` / `14` / — / — |
| `ERP_SECRET` | کلید امضای نشست (در غیر این صورت در `data/secret.key` ساخته می‌شود) | — |
| `ERP_SUPERADMIN_PASSWORD` | گذرواژه‌ی اولیه‌ی superadmin | تصادفی |

## ماژول‌ها (۳۰ موجودیت)

| ماژول | موارد |
|---|---|
| منابع انسانی | واحد سازمانی، کارکنان، مرخصی (گردش تأیید/رد) |
| انبار | کالا، انبار، ورود/خروج، گزارش موجودی (کنترل حداقل موجودی، جلوگیری از موجودی منفی) |
| خرید | تأمین‌کننده، سفارش خرید (پیش‌نویس ← تأیید ← دریافت به انبار) |
| فروش | مشتری (سقف اعتبار)، سفارش/فاکتور فروش (تأیید ← ارسال و خروج از انبار) |
| مالی | دریافت/پرداخت، هزینه‌ها، مانده حساب مشتریان و تأمین‌کنندگان |
| حسابداری | سرفصل حساب‌ها (۲۵ حساب پیش‌فرض)، اسناد دوطرفه، تراز آزمایشی، دفتر معین، **کارت حساب تفصیلی مشتری/تأمین‌کننده**، سود و زیان، ترازنامه، قفل دوره، **بستن سال مالی** |
| تولید | BOM، دستور تولید (با **ضایعات و بازده**)، مراکز کار (نرخ ساعتی، ظرفیت)، MRP، گزارش ظرفیت، ماشین‌آلات و **نگهداری و تعمیرات (PM)** |
| حقوق و دستمزد | پارامترهای بیمه/مالیات پلکانی، دوره‌ی حقوق ماهانه (شمسی)، فیش حقوقی قابل چاپ، سند حسابداری خودکار |
| پروژه (PMO) | پروژه، وظایف (WBS) با محاسبه‌ی خودکار پیشرفت پروژه |
| کیفیت (QA/QMS) | NCR با گردش ریشه‌یابی/CAPA، فهرست مدارک (DCC) |
| مدیریت | کاربران، تنظیمات شرکت، گزارش رویدادها (Audit Log) |

نقش‌ها: مدیر شرکت، مدیر ارشد، HR، انبار، خرید، فروش، مالی، PMO، QA، مشاهده‌گر (+ مدیر کل سامانه).
ماتریس دسترسی در `src/auth.js` است.

## حسابداری دوطرفه

- سند دستی: پیش‌نویس ← **قطعی** (ثبت در دفتر کل؛ سند نامتوازن رد می‌شود) ← **برگشت** (سند معکوس). سند قطعی قابل ویرایش/حذف نیست.
- **سندهای خودکار** (وقتی ماژول حسابداری فعال است):

| رویداد | بدهکار | بستانکار |
|---|---|---|
| دریافت سفارش خرید | موجودی کالا/مواد، مالیات قابل استرداد | حساب‌های پرداختنی |
| ارسال و فاکتور فروش | حساب‌های دریافتنی؛ بهای تمام‌شده | فروش، مالیات پرداختنی؛ موجودی کالا |
| دریافت از مشتری | بانک/صندوق | حساب‌های دریافتنی |
| پرداخت به تأمین‌کننده | حساب‌های پرداختنی | بانک/صندوق |
| هزینه | حساب هزینه‌ی دسته‌ی مربوط | بانک/صندوق |
| تکمیل دستور تولید | موجودی کالای ساخته‌شده | موجودی مواد + دستمزد و سربار جذب‌شده |

- ویرایش/حذف دریافت، پرداخت یا هزینه، سند خودکار قبلی را برگشت می‌دهد و سند جدید می‌زند. سندهای خودکار را فقط از مبدأ می‌توان اصلاح کرد.
- **بهای تمام‌شده**: میانگین موزون متحرک؛ با هر دریافت خرید یا تکمیل تولید، قیمت تمام‌شده‌ی کالا به‌روز می‌شود.
- **بستن دوره**: در «تنظیمات شرکت» تاریخ قفل را بدهید؛ ثبت سند در آن تاریخ و قبل از آن رد می‌شود.
- **حساب تفصیلی**: ردیف‌های دریافتنی/پرداختنی در اسناد خودکار طرف‌حساب (مشتری/تأمین‌کننده) دارند؛ در سند دستی هم می‌توان طرف‌حساب را انتخاب کرد. گزارش «کارت حساب» جمع تفصیلی را با حساب کل تطبیق می‌دهد و مبلغ بدون طرف‌حساب را نشان می‌دهد.
- **بستن سال مالی** (تنظیمات شرکت): حساب‌های درآمد/هزینه تا تاریخ انتخابی صفر و سود/زیان به «سود (زیان) انباشته» منتقل می‌شود (سند منشأ «بستن سال»)، و دوره قفل می‌شود. صورت سود و زیان تحت تأثیر سند بستن نیست. بازگشایی: برداشتن قفل + برگشت سند بستن. اسناد پیش‌نویس مانع بستن‌اند.
- شرکت جدید با سرفصل پیش‌فرض ساخته می‌شود؛ حساب‌های سیستمی (کلیددار) حذف نمی‌شوند.

## تولید

- **BOM**: مواد هر بچ + دستمزد/سربار ثابت + مرکز کار و ساعت کار هر بچ + درصد ضایعات برنامه‌ای (برای MRP).
- **دستور تولید**: پیش‌نویس ← آزاد ← **تکمیل**. تکمیل: کنترل موجودی، خروج مواد برای (سالم + ضایعات)، ورود محصول سالم، محاسبه‌ی بهای واحد و ثبت سند. هزینه‌ی ضایعات روی محصول سالم جذب می‌شود؛ بازده (٪) و هزینه‌ی ضایعات ثبت می‌شود. دستمزد/سربار = مبلغ ثابت BOM + ساعت کار × نرخ ساعتی مرکز کار.
- **ظرفیت**: بار ساعتی دستورهای باز هر مرکز کار در برابر ظرفیت روزانه (روز کاری لازم). **MRP**: کسری مواد با احتساب موجودی و خریدهای تأییدشده.
- **نگهداری (PM)**: ماشین با دوره‌ی PM؛ تاریخ PM بعدی خودکار؛ گزارش عقب‌افتاده/نزدیک؛ دکمه‌ی «ساخت دستورکار PM» برای سررسیده‌ها (بدون تکرار). دستورکار اصلاحی، ماشین را «خراب» می‌کند. پایان دستورکار: به‌روزرسانی PM ماشین، ثبت ساعت توقف، و سند هزینه (تعمیر و نگهداری ← بانک).

## PostgreSQL

```bash
npm install            # بسته‌ی اختیاری pg نصب می‌شود
export DATABASE_URL=postgres://erp:secret@localhost:5432/erp
npm start              # جدول‌ها در اولین اجرا ساخته می‌شوند (CREATE TABLE IF NOT EXISTS + ALTER ADD COLUMN)
```

- همان کد روی هر دو پشتیبان اجرا می‌شود؛ **هر ۶۱ تست روی SQLite و PostgreSQL پاس می‌شود** (اجرا روی PostgreSQL: `TEST_DATABASE_URL=postgres://… npm test` — schema آن دیتابیس پاک می‌شود، فقط روی دیتابیس آزمایشی بزنید).
- در PostgreSQL هر عملیات تغییردهنده در یک تراکنش با قفل مشورتی (advisory lock) روی شرکت اجرا می‌شود (جلوگیری از رقابت روی موجودی و شماره‌گذاری)؛ در SQLite درخواست‌ها پشت‌سرهم اجرا می‌شوند.
- مهاجرت از SQLite موجود به PostgreSQL **ابزار خودکار ندارد** (طرح یکسان است؛ با `pgloader` یا اسکریپت خودتان قابل انجام است). پایگاه‌های SQLite قدیمی با هر نسخه به‌صورت خودکار ارتقا می‌یابند.
- فایل‌های پیوست روی دیسک (`ERP_FILES_DIR`) ذخیره می‌شوند؛ در استقرار چندسرور باید پوشه‌ی مشترک (NFS/volume) باشد و در پشتیبان‌گیری همراه دیتابیس نگه داشته شود.

## پیوست فایل

هر رکورد (سفارش، سند، NCR، کارمند، …) تا ۲۵ پیوست می‌گیرد. مجاز: pdf، تصویر، Excel/Word/PowerPoint، zip، txt، csv، dwg/dxf (حداکثر ۱۰MB). دسترسی همان دسترسی رکورد است (مشاهده = دانلود؛ ایجاد/ویرایش = آپلود؛ ویرایش = حذف)، فایل‌ها بین شرکت‌ها جدا و همیشه به‌صورت دانلود (`attachment` + `nosniff`) ارائه می‌شوند، و با حذف رکورد پاک می‌شوند. فایل‌ها **اسکن ویروس نمی‌شوند**.

## حقوق و دستمزد

1. **پارامترها** (یک‌بار): سهم بیمه‌ی کارمند/کارفرما، سقف بیمه، ضریب اضافه‌کاری، پله‌های مالیات ماهانه. ⚠ مقادیر نمونه‌ی آموزشی‌اند؛ نرخ‌ها، سقف و پله‌های سال جاری را حسابدار مطابق قانون تنظیم کند.
2. **دوره‌ی حقوق**: سال/ماه شمسی ← «ایجاد فیش‌ها» برای کارکنان شاغل (مرخصی بدون حقوقِ تأییدشده خودکار کسر می‌شود) ← ویرایش اضافه‌کاری/پاداش/کسورات هر فیش ← «تأیید» (سند حسابداری: هزینه‌ی حقوق و سهم کارفرما ← حقوق/بیمه/مالیات پرداختنی) ← «ثبت پرداخت» (بدهی حقوق ← بانک). لغو دوره‌ی تأییدشده سند را برگشت می‌دهد.
3. فرمول: حقوق پایه متناسب با روزهای کارکرد؛ اضافه‌کاری = ساعت × (پایه ÷ (۳۰×ساعت روزانه)) × ضریب؛ بیمه روی ناخالص (تا سقف)؛ مالیات پلکانی روی (ناخالص − بیمه‌ی کارمند).

## استقرار، پشتیبان‌گیری و امنیت

- **`DEPLOY.md`** — استقرار با Docker Compose (PostgreSQL + Caddy با HTTPS خودکار + پشتیبان روزانه رمزنگاری‌شده) یا systemd/Nginx؛ بازیابی، تمرین بازیابی، پایش، فهرست سخت‌سازی.
- **`SECURITY.md`** — یافته‌های بازبینی امنیتی (رفع‌شده)، آنچه بررسی شد، و ریسک‌های باقی‌مانده.
- پشتیبان: `npm run backup` | `backup:verify <فایل>` | `backup:restore <فایل> --force` | `backup:list`.
- سلامت: `GET /api/health` (بدون احراز هویت).

## معماری

- `src/entities.js` — **تعریف اعلانی** همه‌ی موجودیت‌ها (فیلدها، اعتبارسنجی، قوانین، عملیات). برای افزودن موجودیت/ماژول جدید فقط همین‌جا یک تعریف اضافه کنید؛ جدول، API، فرم، لیست، CSV و دسترسی خودکار ساخته می‌شود.
- `src/engine.js` — موتور CRUD عمومی (همه‌ی کوئری‌ها با `company_id`، شماره‌گذاری خودکار، Audit).
- `src/server.js` — HTTP API، احراز هویت، گزارش‌ها و داشبورد. `public/` — رابط SPA.

## امنیت

گذرواژه با scrypt؛ نشست امضاشده با کوکی HttpOnly + SameSite=Strict؛ هدر `X-ERP` برای درخواست‌های تغییردهنده (CSRF)؛
محدودسازی تلاش ورود؛ CSP؛ ایزولاسیون شرکت‌ها در همه‌ی کوئری‌ها و در ارجاع بین رکوردها؛ جلوگیری از Formula Injection در CSV.
پشت HTTPS (مثلاً Nginx/Caddy با `X-Forwarded-Proto: https`) مستقر کنید.

## محدودیت‌های فعلی (صادقانه)

- حسابداری: تک‌ارزی؛ بدون مرکز هزینه و تفصیلی غیر از مشتری/تأمین‌کننده؛ بستن سال یک سند ساده است (بدون سند افتتاحیه‌ی خودکار سال بعد).
- ورود/خروج دستی انبار سند حسابداری ایجاد نمی‌کند (موجودی اول دوره را با سند دستی ثبت کنید). برگشت سند فروش/خرید پس از ارسال/دریافت پشتیبانی نمی‌شود.
- سندهای قبل از به‌روزرسانی در دیتابیس‌های قدیمی به‌صورت خودکار ثبت نمی‌شوند؛ فقط سرفصل و ماژول اضافه می‌شود.
- مالیات خرید/فروش درصد ثابت روی سفارش است (بدون دوره‌ی اظهارنامه). تولید: ظرفیت فقط گزارشی است (بدون گانت)؛ ضایعات در سطح دستور؛ PM زمان‌پایه.
- حقوق: **تولید لیست بیمه (DSKWOR)، اظهارنامه‌ی مالیات حقوق، عیدی، سنوات و مرخصی ذخیره، وام/اقساط خودکار و حضور و غیاب وجود ندارد**؛ فقط مرخصی بدون حقوق از ماژول مرخصی لحاظ می‌شود. پرداخت بیمه/مالیات به سازمان‌ها را با سند دستی ثبت کنید.
- پیوست: بدون اسکن ویروس، بدون پیش‌نمایش درون‌برنامه‌ای؛ اعلان ایمیلی وجود ندارد.
- مهاجرت خودکار SQLite ← PostgreSQL وجود ندارد.
- حذف تراکنش ورود انبار دستی می‌تواند موجودی را منفی کند (فقط کاربر دارای دسترسی حذف).
